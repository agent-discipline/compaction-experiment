S3 단계입니다. 같은 사용자가 탭 여러 개로 **서로 다른 좌석을** 동시에 누르면 모든 요청이 같은 매수를 읽고 통과해서 1인 2매를 넘깁니다. 좌석 락은 좌석마다 행이 달라서 이걸 막지 못합니다. 사용자 단위 직렬화를 이렇게 넣어 주세요.

- 방식: **PostgreSQL 어드바이저리 락 시도**. 선점 트랜잭션 안에서, 좌석을 읽기 **전에** `SELECT pg_try_advisory_xact_lock(:scheduleId, :userId)`를 부릅니다(정수 키 두 개 — 회차 id, 사용자 id. int 범위를 넘는 id는 조용히 자르지 말고 실패시키세요). 결과는 기다리지 않고 바로 `true`/`false`로 돌아옵니다.
- 선점 흐름은 트랜잭션 하나에서 이 순서입니다:
  1. 어드바이저리 락 시도(위). 결과만 기억해 두고 다음으로 넘어갑니다.
  2. 좌석 확인 — 지금과 같습니다: 좌석을 `NOWAIT` 잠금으로 읽어 없으면 404 `SEAT_NOT_FOUND`, 잠겨 있거나 `AVAILABLE`이 아니면 409 `SEAT_NOT_AVAILABLE`.
  3. 매수 판정: 1에서 `false`였으면(같은 사용자의 다른 선점이 진행 중) 기다리지 않고 409 `HOLD_LIMIT_EXCEEDED`. `true`였으면 지금과 같은 매수 확인(그 회차의 홀드 수 + `CONFIRMED` 예약 수 < 2, 아니면 409 `HOLD_LIMIT_EXCEEDED`)을 같은 트랜잭션 안에서 합니다.
  4. 좌석 `HELD` + 홀드 생성.
- 그래서 락을 못 잡은 요청도 **좌석 확인을 먼저 한 뒤** 거절됩니다(좌석 불가가 매수 초과보다 먼저인 순서는 그대로). 락 시도에 실패했다고 2번보다 앞에서 거절하지 마세요. 새 에러 코드는 만들지 않습니다.
- 락 순서는 사용자 → 좌석입니다. 좌석 락이 NOWAIT라 사용자 락을 쥔 채 좌석을 기다리는 일은 없습니다.
- `_xact_` 락이라 트랜잭션이 끝날 때(성공이든 롤백이든) DB가 풉니다. 세션 락(`pg_advisory_lock`)과 기다리는 `pg_advisory_xact_lock`은 쓰지 마세요.
- 이 락은 선점에서만 잡습니다. 확정·만료 경로는 이 단계에서 바꾸지 않습니다.
- 이 방식을 설정 값으로 남겨 주세요: `seat.hold.limit-strategy: advisory-try`. 지금은 이 값 하나만 지원하고, 다른 값이면 기동이 실패하게 합니다.

테스트: 같은 사용자가 서로 다른 좌석 10개에 동시에 선점하면 성공이 2건을 넘지 않고, 끝 상태의 그 사용자 홀드 + 확정 수도 2 이하. 다른 사용자끼리는 서로 막히지 않는지도 확인해 주세요. 테스트는 통과시켜 주세요.
