S7 단계입니다. S6의 조건부 확정으로 늦은 확정은 "명확한 거부"가 됐지만, 결제가 홀드 만료보다 늦게 끝난 사용자는 여전히 돈을 내고 좌석을 잃습니다. 그 수를 줄이려고 **확정 기본 방식을 "결제 중 홀드 연장"으로 바꿉니다.** S6에서 정한 `seat.confirm.mode: conditional`(유일한 방식)을 **`seat.confirm.mode: conditional-extend`(기본값)**로 대체합니다. 확정 문장(C1~C3)·유니크 인덱스·조건부 배치는 그대로 씁니다 — 바뀌는 것은 결제 시작 시점의 연장과 결제 마감 시각 안내입니다. `conditional`도 설정으로 고를 수 있게 남겨 둡니다.

## 설정 (application.yml)

```yaml
seat:
  confirm:
    mode: conditional-extend
    payment-window: 611s        # W — 연장 뒤 남는 시간
    payment-min-remaining: 1s   # θ — 결제 시작을 받는 최소 남은 시간
    pay-by-margin: 1s           # M — 결제 마감 = 만료 − M
```

- `pay-by-margin`이 `payment-min-remaining`보다 크거나, 둘 중 하나가 음수이거나, `conditional-extend`인데 `payment-window`가 0 이하이면 **기동을 실패**시켜 주세요(조용히 기본값으로 돌지 않게).

## 연장 표지 컬럼

```sql
ALTER TABLE seat_hold ADD COLUMN extended_at TIMESTAMPTZ NULL;   -- 첫 연장 시각, NULL = 연장 안 함
```

한 홀드는 **많아야 한 번** 연장됩니다.

## 새 API — 결제 시작

`POST /api/holds/{holdId}/payment-start` · 헤더 `X-User-Id` · 본문 없음. 클라이언트가 사용자를 결제 화면으로 보내기 직전에 부릅니다(권고 — 확정은 이 호출 여부를 검사하지 않습니다).

성공 `200`:
```json
{"holdId": 1, "expiresAt": "...", "payBy": "...", "payWithinSeconds": 609, "extended": true}
```

`conditional-extend`의 동작(`:now` = 결제 시작 처리마다 한 번 정한 기준 시각, 바인드 값):

```sql
-- E1 첫 연장: 내 것 · 살아 있음 · 아직 연장 안 함 · 연장이 실제로 늘리는 경우만
UPDATE seat_hold
   SET expires_at = :now + :window, extended_at = :now
 WHERE id = :holdId AND user_id = :userId
   AND extended_at IS NULL
   AND expires_at > :now + :minRemaining
   AND expires_at < :now + :window
RETURNING expires_at;
```

- 1행이면 200, `extended: true`, `expiresAt` = 새 만료.
- 0행이면 잠금 없는 진단(`SELECT user_id, expires_at, extended_at FROM seat_hold WHERE id = ?`)으로, 위에서부터 첫 일치:
  1. 행 없음 → 404 `HOLD_NOT_FOUND`
  2. 남의 것 → 403 `HOLD_NOT_OWNED`
  3. `expires_at <= :now` → 409 `HOLD_EXPIRED`
  4. `extended_at IS NOT NULL`(이미 연장) → 200, 지금 `expiresAt`, `extended: true` — 재호출은 다시 연장하지 않습니다
  5. `expires_at <= :now + :minRemaining`(연장하기엔 늦음) → 409 `HOLD_EXPIRED`
  6. `expires_at >= :now + :window`(이미 충분히 남음) → 200, 지금 `expiresAt`, `extended: false`, 표지도 남기지 않음
  7. 그 밖(생기지 않아야 함) → ERROR 로그 + 409 `HOLD_EXPIRED`
- 새 에러 코드는 만들지 않습니다.
- 회차가 판매 마감(`starts_at`)을 지났어도 위 규칙 그대로 연장합니다 — 마감 전에 잡은 홀드의 확정을 막지 않는 것과 같은 이유입니다.

`conditional`을 고른 경우 같은 API는 **아무 행도 쓰지 않는 확인**만 합니다: 없음 404 → 남의 것 403 → 만료 409 `HOLD_EXPIRED` → `expires_at - :now <= :minRemaining`이면 409 `HOLD_EXPIRED` → 그 밖 200(지금 `expiresAt`, `extended: false`). 이 200은 남은 시간을 보장하지 않습니다(홀드는 원래 만료 시각에 만료).

## 결제 마감 시각

- `payBy = expiresAt − pay-by-margin`, `payWithinSeconds = max(0, ⌊(payBy − 응답 시각) / 1초⌋)`.
- **선점 201 응답에도** `payBy`와 `payWithinSeconds`를 더합니다(`holdId`, `seatId`, `expiresAt`에 추가). 결제 시작 200에도 같은 규칙으로 넣습니다.
- 서버는 알려 주기만 하고, 결제 제한 시간으로 강제하는 것은 결제 쪽 몫입니다.

## 배치와의 관계

연장된 홀드는 `expires_at`이 늦춰졌으므로 만료 배치가 지우지 않습니다. 원래 만료 시각을 지나도 살아 있고 확정될 수 있어야 합니다.

테스트: 선점 → 결제 시작 → 200, `extended: true`, `expiresAt`이 약 611초 뒤, `payBy = expiresAt − 1초`, DB의 `extended_at`이 채워짐. 다시 부르면 같은 `expiresAt`. 남의 홀드 403 · 없는 홀드 404 · 만료 홀드 409. 선점 201의 `payBy`·`payWithinSeconds`. 짧은 TTL로 연장한 홀드가 원래 만료 뒤 배치를 지나도 살아 있고 확정 200. 잘못된 설정 조합의 기동 실패. 테스트는 통과시켜 주세요.
