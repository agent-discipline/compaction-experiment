S0 단계입니다. 공연 좌석 예약 서비스의 기본 기능을 만들어 주세요. 이번 단계는 동시성 제어 없이 "기능이 되는" 평범한 구현이 목표입니다. 여러 요청이 동시에 같은 좌석을 누르는 경우 같은 동시성 문제는 다음 단계들에서 하나씩 다루니, 이번에는 락·유니크 제약 같은 장치를 넣지 마세요.

## 도메인

- 상품(공연) 1 — N 회차(공연 × 일시) 1 — N 좌석. 판매 단위는 **회차의 좌석**입니다(같은 A-12도 회차가 다르면 다른 재고).
- 좌석은 상태를 저장합니다: `AVAILABLE` → `HELD`(선점) → `RESERVED`(확정). 만료되면 `HELD` → `AVAILABLE`.
- 선점(홀드)은 유효 시간이 있는 일시 점유입니다. 홀드 테이블에는 **살아 있는 홀드만** 행으로 둡니다 — 확정되거나 만료되면 홀드 행을 지웁니다(상태 컬럼 없음).
- 예약은 결제로 확정된 사실입니다. 예약 1행 = 좌석 1석. 상태는 `CONFIRMED` / `CANCELED`(취소 API는 아직 만들지 않습니다).

## 테이블

서로게이트 PK와 FK만 둡니다. 유니크 제약·CHECK·조회용 인덱스는 이번 단계에 넣지 마세요.

```sql
CREATE TABLE product (
    id    BIGSERIAL    PRIMARY KEY,
    name  VARCHAR(200) NOT NULL
);

CREATE TABLE product_schedule (
    id          BIGSERIAL   PRIMARY KEY,
    product_id  BIGINT      NOT NULL REFERENCES product (id),
    starts_at   TIMESTAMPTZ NOT NULL
);

CREATE TABLE product_seat (
    id           BIGSERIAL   PRIMARY KEY,
    schedule_id  BIGINT      NOT NULL REFERENCES product_schedule (id),
    section      VARCHAR(20) NOT NULL,
    row_no       INT         NOT NULL,
    seat_no      INT         NOT NULL,
    status       VARCHAR(20) NOT NULL
);

CREATE TABLE seat_hold (
    id           BIGSERIAL   PRIMARY KEY,
    seat_id      BIGINT      NOT NULL REFERENCES product_seat (id),
    schedule_id  BIGINT      NOT NULL REFERENCES product_schedule (id),
    user_id      BIGINT      NOT NULL,
    held_at      TIMESTAMPTZ NOT NULL,
    expires_at   TIMESTAMPTZ NOT NULL
);

CREATE TABLE reservation (
    id           BIGSERIAL   PRIMARY KEY,
    schedule_id  BIGINT      NOT NULL REFERENCES product_schedule (id),
    seat_id      BIGINT      NOT NULL REFERENCES product_seat (id),
    user_id      BIGINT      NOT NULL,
    payment_uid  VARCHAR(64) NOT NULL,
    status       VARCHAR(20) NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL
);
```

- `product_seat.status`에는 `AVAILABLE`·`HELD`·`RESERVED`, `reservation.status`에는 `CONFIRMED`·`CANCELED`를 **이름 문자열 그대로** 저장합니다(숫자 코드 아님).
- 홀드의 `held_at`은 선점 시각, 예약의 `created_at`은 확정 시각입니다.

JPA를 쓴다면 `spring.jpa.hibernate.ddl-auto`는 `validate`로 두세요(스키마는 마이그레이션만 만듭니다).

## API

사용자 식별은 요청 헤더 `X-User-Id`(숫자)입니다. 인증은 범위 밖입니다.

| 메서드 | 경로 | 요청 본문 | 성공 | 실패 |
|---|---|---|---|---|
| POST | `/api/schedules/{scheduleId}/seats/{seatId}/hold` | 없음 | `201` `{"holdId", "seatId", "expiresAt"}` | `404 SEAT_NOT_FOUND` · `409 SEAT_NOT_AVAILABLE` · `409 HOLD_LIMIT_EXCEEDED` |
| POST | `/api/holds/{holdId}/confirm` | `{"paymentUid": "..."}` | `200` `{"reservationId", "seatId", "status"}` | `404 HOLD_NOT_FOUND` · `403 HOLD_NOT_OWNED` · `409 HOLD_EXPIRED` · `409 SEAT_NOT_HELD` |

- 실패 응답 본문은 `{"code": "<에러 코드>", "message": "<사람이 읽는 설명>"}` 두 필드입니다. `code`는 위 표의 이름 그대로입니다.
- `holdId`·`seatId`·`reservationId`는 JSON 숫자, `expiresAt`은 ISO-8601 시각 문자열로 내보냅니다.
- 좌석이 그 회차의 좌석이 아니면(회차 id와 좌석 id 짝이 안 맞으면) 좌석 없음 404입니다.
- 확정 API는 "결제가 성공했다"는 결과를 받는 자리입니다. 결제 자체는 범위 밖이고 `paymentUid`는 그대로 예약에 저장합니다. 확정 응답의 `status`는 `"CONFIRMED"`입니다.

## 규칙

| 규칙 | 값 | 설정 키 |
|---|---|---|
| 홀드 유효 시간 | 5분 | `seat.hold.ttl: 5m` |
| 1인 최대 매수 | (사용자, 회차)당 2매 = 홀드 행 수 + `CONFIRMED` 예약 수 | `seat.hold.max-per-user: 2` |
| 만료 배치 주기 | 10초 | `seat.hold.expiry-interval: 10s` |
| 1회 선점 매수 | 1석 | — |

세 값은 `application.yml`에 위 키 이름 그대로 두고 코드가 거기서 읽게 해 주세요(테스트에서 바꿔 끼울 수 있어야 합니다).

## 판정 순서

- **선점**: 좌석 존재 확인(404) → 좌석의 저장된 `status`가 `AVAILABLE`인지(아니면 409 `SEAT_NOT_AVAILABLE`) → 매수 확인: 그 회차에서 이 사용자의 홀드 행 수 + `CONFIRMED` 예약 수가 `seat.hold.max-per-user` 미만인지(아니면 409 `HOLD_LIMIT_EXCEEDED`) → 좌석 `HELD` + 홀드 생성(`held_at = 지금`, `expires_at = 지금 + ttl`).
  - 만료 시각이 지났어도 배치가 아직 지우지 않은 홀드 행은 셉니다.
  - 좌석 판정도 저장된 `status`로만 합니다. 홀드가 만료됐어도 배치가 되돌리기 전까지 그 좌석은 `HELD`이므로 `SEAT_NOT_AVAILABLE`입니다.
  - **좌석 불가가 매수 초과보다 먼저**입니다 — 이미 2매를 가진 사용자가 남이 잡은 좌석을 누르면 `SEAT_NOT_AVAILABLE`입니다.
- **확정**: 홀드가 있는가(404 `HOLD_NOT_FOUND`) → 내 홀드인가(403 `HOLD_NOT_OWNED`) → 만료 전인가(409 `HOLD_EXPIRED`) → 좌석이 `HELD`인가(409 `SEAT_NOT_HELD`) → 좌석 `RESERVED` + 홀드 행 삭제 + 예약(`CONFIRMED`) 생성을 **한 트랜잭션**에서.
- **만료 판정**: `expires_at <= 지금`이면 만료입니다(만료 시각 정각은 이미 만료).
- **만료 배치**: `seat.hold.expiry-interval`마다 돌며, 만료된 홀드를 지우고 그 좌석이 `HELD`면 `AVAILABLE`로 되돌립니다. 한 번 도는 것이 트랜잭션 하나입니다.

## 구조

레이어드(`api` → `service` → `domain`)로 나눠 주세요. 좌석과 그 좌석의 홀드는 함께 바뀌므로 상태 검사와 전이는 좌석 쪽 메서드 안에 두고, 서비스는 로드 → 메서드 호출 → 저장 순서만 조율합니다.

이 단계의 동작을 확인하는 테스트(선점·확정의 성공과 각 실패 코드, 판정 순서, 만료 배치)를 직접 작성해 통과시켜 주세요.
