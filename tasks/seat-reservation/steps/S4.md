S4 단계입니다. **지금의 1인 매수 제어 방식(S3의 어드바이저리 락 시도 + 그 뒤 홀드·예약을 세는 매수 COUNT)을 버리고 아래 방식으로 바꿉니다.** 이유: 어드바이저리 방식은 매수가 이미 찬 사용자도 좌석 락을 잠깐 잡기 때문에, 그 요청이 롤백되는 동안 같은 좌석을 누른 다른 사용자가 억울하게 집니다. 새 방식에서는 매수가 찬 사용자가 좌석 락을 아예 잡지 않습니다.

## 바꾸는 것

- `pg_try_advisory_xact_lock` 호출과 그 거절 경로, 선점 때 홀드·예약을 COUNT해서 판정하던 코드를 **지웁니다**(남겨 두지 마세요).
- 설정 값을 `seat.hold.limit-strategy: counter-upsert-precheck`로 바꿉니다. 지원하는 값은 이것 하나입니다(`advisory-try` 포함 다른 값이면 기동 실패).

## 쿼터 테이블

```sql
CREATE TABLE user_hold_quota (
    schedule_id BIGINT NOT NULL,
    user_id     BIGINT NOT NULL,
    cnt         INT    NOT NULL DEFAULT 0 CHECK (cnt >= 0),
    PRIMARY KEY (schedule_id, user_id)
);
```

- (회차, 사용자)마다 한 행, `cnt` = 그 쌍의 **홀드 행 수 + `CONFIRMED` 예약 수**. 뷰가 아니라 실제 테이블이고, 앱이 직접 맞춰 두는 값입니다.

## 선점 흐름 (트랜잭션 하나, 이 순서)

1. **좌석 선조회(잠금 없음)**: `SELECT status FROM product_seat WHERE id = ? AND schedule_id = ?` — 없으면 404 `SEAT_NOT_FOUND`, `AVAILABLE`이 아니면 409 `SEAT_NOT_AVAILABLE`. 이미 팔린 좌석은 쓰기 없이 여기서 거절합니다.
2. **매수 판정 = 카운터 +1을 한 문장으로**:
   ```sql
   INSERT INTO user_hold_quota (schedule_id, user_id, cnt) VALUES (?, ?, 1)
   ON CONFLICT (schedule_id, user_id) DO UPDATE SET cnt = user_hold_quota.cnt + 1
   WHERE user_hold_quota.cnt + 1 <= ?        -- ? = seat.hold.max-per-user
   ```
   영향 행 1 = 통과, 0 = 매수 초과. 행이 없으면 INSERT 갈래가 cnt = 1로 만들고, 같은 사용자의 동시 요청은 이 행의 락에서 줄을 섭니다. 트랜잭션 밖에서 쿼터 행을 미리 만드는 준비 단계는 두지 마세요(요청당 커넥션은 한 번만 빌립니다).
3. 영향 행이 0이면 좌석을 **다시 한 번 잠금 없이** 읽어서, 그 사이 좌석이 불가가 됐으면 409 `SEAT_NOT_AVAILABLE`, 아니면 409 `HOLD_LIMIT_EXCEEDED`.
4. 그다음에 기존대로 좌석 행을 NOWAIT로 잠가 읽고 `AVAILABLE`을 다시 확인한 뒤 홀드를 만듭니다(매수는 2번에서 끝났으므로 여기서 다시 세지 않습니다). 여기서 지면(좌석 409) 트랜잭션 전체가 롤백되므로 카운터 +1도 함께 되돌아가야 합니다.

에러 순서는 여전히 좌석 불가 → 매수 초과입니다. 남는 틈 하나는 받아들입니다: 다른 트랜잭션이 아직 끝나지 않은 채 잡고 있는 좌석은 잠금 없는 읽기에 `AVAILABLE`로 보이므로, 그 순간 매수가 찬 사용자는 `HOLD_LIMIT_EXCEEDED`를 받을 수 있습니다.

## 카운터를 바꾸는 경로

- 선점 성공: +1(위 2번).
- 확정: 그대로(홀드 −1, 예약 +1).
- 만료 배치: 실제로 지운 홀드 수만큼 (회차, 사용자)별로 내립니다 — `UPDATE user_hold_quota SET cnt = cnt - ? WHERE schedule_id = ? AND user_id = ?`. 쿼터 행이 없으면(영향 행 0) 조용히 넘기지 말고 예외로 실패시키세요. 음수는 CHECK가 막습니다.
- 만료로 `cnt`가 0이 돼도 쿼터 행은 지우지 않습니다(행은 `cnt = 0`으로 남습니다).

## 기존 데이터 백필

이미 있는 홀드·확정 예약이 카운터에 들어가 있지 않으므로, 앱 코드가 아니라 스키마 변경과 함께 마이그레이션에서 채웁니다. 한 트랜잭션에서:

1. `LOCK TABLE seat_hold, reservation, user_hold_quota IN SHARE ROW EXCLUSIVE MODE;`
2. 실제 값이 1 이상인 쌍: `seat_hold` 행 전체 수(만료 지난 미삭제 홀드 포함) + `reservation` `CONFIRMED` 수를 (회차, 사용자)별로 합쳐 `INSERT … ON CONFLICT (schedule_id, user_id) DO UPDATE SET cnt = EXCLUDED.cnt WHERE user_hold_quota.cnt <> EXCLUDED.cnt`. 회차는 홀드·예약 자신의 `schedule_id`를 씁니다. 합계는 `sum(...)::int`.
3. 실제 값이 0인데 `cnt`가 0이 아닌 기존 행: `cnt = 0`으로(행은 지우지 않습니다).

빈 DB에서는 아무 행도 만들지 않고, 두 번 돌려도 결과가 같아야 합니다. 상한(2)을 넘는 실제 값도 그대로 둡니다.

테스트: 같은 사용자가 서로 다른 좌석 10개에 동시에 선점하면 성공이 **정확히 2건**이고 `cnt = 2`, 나머지는 409 `HOLD_LIMIT_EXCEEDED`. 처음 보는 사용자의 동시 요청(쿼터 행이 없는 상태)도 정확히 2건. 좌석에서 진 선점 뒤 `cnt`가 그대로인지, 확정 뒤 `cnt`가 그대로인지, 만료 뒤 내려가는지, 백필이 섞인 데이터에서 `cnt = 홀드 + 확정`을 만드는지 확인해 주세요. 테스트는 통과시켜 주세요.
