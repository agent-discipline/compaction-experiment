S1 단계입니다. 선점 경로의 조회가 홀드·예약 테이블 전체를 훑고 있어서 DB 기본기를 먼저 갖추려고 합니다. 아래 일반 인덱스 5개를 이름 그대로 추가해 주세요.

| 인덱스 이름 | 대상 | 쓰는 곳 |
|---|---|---|
| `idx_seat_hold_seat_id` | `seat_hold (seat_id)` | 좌석의 홀드 목록 조회, FK |
| `idx_seat_hold_user_id` | `seat_hold (user_id)` | 1인 매수 확인 — 홀드 수 |
| `idx_seat_hold_expires_at` | `seat_hold (expires_at)` | 만료 배치 조회 |
| `idx_reservation_schedule_user` | `reservation (schedule_id, user_id)` | 1인 매수 확인 — 확정 예약 수 |
| `idx_reservation_seat_id` | `reservation (seat_id)` | FK |

- **다섯 개 모두 유니크가 아닌 일반 인덱스**입니다. 그리고 제가 따로 정하기 전까지는 어느 단계에서도 유니크 인덱스·유니크 제약을 만들지 마세요(기본 키 제외) — 중복을 막는 장치는 조회 속도와 섞이지 않게 나중에 따로 정합니다.
- 홀드 쪽 사용자 인덱스는 `user_id` 단일 컬럼으로 둡니다. 사용자 한 명의 홀드는 몇 개뿐이라 `user_id`만으로 충분히 좁혀지고, 홀드 수 조회의 회차 조건이 홀드 테이블 컬럼에 걸리든 조인한 좌석 테이블 컬럼에 걸리든 쓰일 수 있습니다. `seat_hold(schedule_id, user_id)` 복합 인덱스로 바꾸지 마세요 — 회차 조건이 좌석 쪽에 걸린 조회에서는 앞 열이 조건에 없어 그 인덱스가 쓰이지 않습니다.
- 커넥션 풀 크기는 10으로 고정합니다. `application.yml`에 `spring.datasource.hikari.maximum-pool-size: 10`을 명시해 주세요.

인덱스 다섯 개가 이름·컬럼 그대로 있고 유니크가 아니라는 것, 그래서 같은 좌석에 홀드 행 두 개를 직접 넣어도 DB가 막지 않는다는 것을 확인하는 테스트를 작성해 통과시켜 주세요.
