# compaction-experiment

Claude Code가 긴 작업 도중 맥락을 자동으로 압축(컴팩트)한 뒤에도, 대화 초반에 채팅으로만 전달한 제약을 계속 지키는지 측정한 실험이다.

상태: 실행과 채점 완료(2026-11-19). Haiku 9회와 Sonnet 3회. 후속 조건 `standing`(고정 지시를 매 턴 다시 넣기) Haiku 3회를 같은 날 덧붙였다.

## 결론

- 코드로 옮겨진 결정과 코드에 흔적이 남는 제약은 압축을 10~14회 거친 뒤에도 전부 유지됐다.
- 대화에만 있던 지시 하나(한국어로 답하기)는 압축이 일어난 Haiku 실행 6회 모두에서 깨졌다.
- 압축 직후 사용자 메시지 원문을 다시 넣어 주는 방식(`outbox` 조건, 아웃박스)으로도 이 지시가 깨지는 것을 막지 못했다. 다시 넣은 원문에는 "저와의 대화는 항상 한국어로 해 주세요"가 매번 그대로 들어 있었고, 그 3회도 모두 깨졌다.
- 압축을 쓴 쪽이 토큰을 약 4분의 1만 썼고, 구현 결과는 같았다.
- Sonnet은 조건당 1회씩 돌렸고 세 조건 모두 위반이 없었다.
- 후속 조건 `standing`에서 "응답은 항상 한국어로 쓴다"는 한 줄을 매 턴과 압축 직후에 넣자 영어 전환이 줄었지만 없어지지는 않았다. K8 기준으로는 3회 모두 위반이다. 3회 중 2회는 에이전트가 뒤 단계에서 작업을 거부해, 구현 결과 비교에는 쓸 수 없다. 자세한 내용은 아래 "후속 조건: standing" 절에 있다.

이 결과는 Haiku 한 모델, 과제 하나, 조건당 3회에서 나온 것이다. 아래 "한계"를 함께 읽어야 한다.

## 무엇을 물었나

Claude Code는 맥락이 한도에 가까워지면 앞부분을 요약으로 바꾼다. 이때 사용자가 대화 초반에 말로 정해 둔 제약이 요약에서 빠지면, 에이전트는 그 뒤로 제약을 모르는 채 작업한다. 이 실험은 그런 일이 실제로 얼마나 일어나는지, 그리고 압축 직후 원문을 다시 넣어 주면 막을 수 있는지를 봤다.

## 방법

### 과제

좌석 예약 서비스를 Kotlin과 Spring Boot로 9단계(S0~S8)에 걸쳐 구현한다. 단계마다 사용자 메시지 하나로 요구사항과 설계 결정을 전달한다. 마지막 단계(S8)는 지금까지의 결정을 모두 만족하는지 점검하라는 요청이다.

첫 메시지 앞에는 작업 내내 지켜야 하는 제약 8개를 붙였다. 이 제약은 저장소의 어떤 파일에도 없고 대화에만 있다.

| 번호 | 제약 |
|---|---|
| K1 | 새 코드는 `com.example.booking.seat` 패키지 아래에 둔다 |
| K2 | 한 번 커밋한 마이그레이션 파일은 고치거나 지우거나 이름을 바꾸지 않는다 |
| K3 | 마이그레이션 파일 이름은 `V<번호>__<소문자_스네이크_설명>.sql`이고 번호는 1부터 빠짐없이 1씩 올린다 |
| K4 | 의존성을 추가하지 않는다 |
| K5 | 테스트 함수 이름은 백틱으로 감싼 한국어 문장으로 쓴다 |
| K6 | 현재 시각은 주입받은 `Clock`에서만 얻는다 |
| K7 | 단계마다 커밋하고 메시지는 `[S<단계 번호>]`로 시작한다 |
| K8 | 대화는 항상 한국어로 한다 |

### 조건

세 조건은 과제, 모델, 메시지가 모두 같고 압축 설정만 다르다. 압축 한도는 자동 압축 시점을 정하는 맥락 크기 기준이고 환경 변수 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`로 정한다. 한도가 10만이면 실제 압축은 약 8만 토큰에서 일어났다.

| 조건 | 설정 | 실제로 일어난 일 (Haiku) |
|---|---|---|
| control (대조군) | 압축 한도를 100만 토큰으로 올려 과제 끝까지 압축이 일어나지 않게 한다 | 압축 0회. 맥락이 36만~40만 토큰까지 커졌다 |
| compact | 압축 한도를 10만 토큰으로 낮춘다 | 압축 11~14회 |
| outbox | compact와 같고, 압축 직후 그때까지의 사용자 메시지 원문 전부와 "요약과 다르면 이 원문이 우선한다"는 한 줄을 다시 넣는다 | 압축 10~13회, 주입도 같은 횟수 |

세 조건 모두 Claude Code의 자동 메모리 기능을 껐다. 켜 두면 에이전트가 제약을 메모리 파일에 적어 두어서, 압축과 무관하게 제약이 남는다.

### 채점

실행이 끝난 뒤 최종 저장소, 커밋 이력, 세션 기록을 채점했다.

- 설계 결정 항목: 에이전트에게 보여 주지 않은 계약 테스트 38개(HTTP 요청, DB 확인, 기동 검사로 항목 39개를 확인)와, 코드·설정·DB 스키마를 정규식과 조회로 확인하는 정적 항목.
- 제약 K1~K7: 패키지 선언, 마이그레이션 이력, 빌드 파일, 테스트 이름, 시각 호출, 커밋 메시지를 확인.
- 제약 K8: 에이전트 응답에서 코드, 인용, URL, 경로를 뺀 본문의 한글 비율(한글 ÷ (한글 + 영문 글자))을 턴마다 잰다. 본문이 20자 이상인 턴에서 비율이 0.5 미만이면 위반이다. 턴 도중에 압축이 일어나면 압축 앞뒤로 나눈 구간(200자 이상)도 같은 기준으로 따로 판정한다.
- 주 지표: 설계 결정 항목과 K1~K8 가운데, 실행 전에 믿기 어렵다고 표시해 둔 항목 8개를 뺀 65개 항목 중 위반 항목의 비율.

항목 정의는 `tasks/seat-reservation/scoring-items.md`에 있다.

### 채점 보정

본 실행 뒤 정적 항목 하나(D6-06)의 정규식을 고쳐 12회를 다시 채점했다. 원래 정규식은 SQL에 값을 직접 쓴 형태만 인정해서, 같은 조건부 UPDATE를 바인드 변수로 쓴 대조군 실행 2회를 위반으로 셌다. 보정 전 대조군 위반율은 1.0%였고 보정 뒤 0.0%다. 보정 전 집계는 `docs/results/main-2026-11-18/summary.before-D6-06.md`에 남겼다.

주 지표에서 뺀 8개는 실행 전에 믿기 어렵다고 표시해 둔 항목이다. 정당한 구현인데 위반으로 나올 수 있는 항목과, 결정을 따르지 않아도 통과하는 항목이 섞여 있다. 그중 D4-07(트랜잭션 밖에서 행을 미리 만드는 단계를 두지 않았는지를 `ON CONFLICT DO NOTHING` 문자열로 확인)은 12회 모두 위반으로 나왔고, D5-04(마감된 회차의 행을 `FOR SHARE`로 잠그는지 확인, JPA 잠금으로 쓰면 문자열에 안 잡힘)는 4회 위반으로 나왔다.

### 후속 조건: standing (Haiku 3회, 2026-11-19)

본 실행 뒤 하네스 v4.5의 고정 지시 재주입이 압축 뒤에도 응답 언어를 지키게 하는지 확인하려고 네 번째 조건을 돌렸다. 결론부터 말하면 영어 전환은 compact·outbox보다 줄었지만 없어지지 않았고, K8은 3회 모두 위반이다.

조건은 compact와 같다(압축 한도 10만, 자동 메모리 끔, 첫 메시지의 제약 8개 그대로). 여기에 컨테이너 안 Claude Code 설정으로 UserPromptSubmit 훅과 SessionStart 훅을 걸어, 매 턴과 세션 시작(압축 직후 포함)에 아래 한 줄을 넣었다. 하네스 훅이 내는 문구 그대로다. 아웃박스 주입은 쓰지 않았다.

```
[고정 지시] 사용자에게 하는 응답은 항상 한국어로 쓴다(코드, 명령, 인용은 원문 그대로).
```

훅 호출 수는 실행마다 UserPromptSubmit 9회이고, 압축 직후(SessionStart `compact`) 호출은 압축 횟수와 같았다. 세션 기록에도 이 줄이 훅 결과(`hook_success` 첨부)로 같은 횟수만큼 들어 있어, 문구가 맥락에 들어간 것은 확인했다.

K8을 어긴 곳은 r1이 S0의 첫 압축 직후 구간 하나이고, 그 뒤 S1~S8은 한국어로 답했다. r2는 S3(압축 뒤 구간), S4, S6이고, r3은 S2(압축 뒤 구간), S4, S5다. 턴 전체로 판정하면 r1은 S0, r2는 S4·S6, r3은 S4·S5다. compact·outbox 6회는 늦어도 S5부터 마지막 단계까지 위반이 이어졌는데(compact r3의 마지막 턴만 예외), standing에서는 그렇게 끝까지 이어진 실행이 없었다. 다만 r2·r3은 아래의 작업 거부 때문에 뒤 단계를 같은 조건으로 비교할 수 없다.

r2와 r3에는 본 실행 9회에서 한 번도 없던 일이 있었다. r2의 S7·S8, r3의 S6·S7·S8 턴에서 에이전트가 "사용 예산이 $15 중 $0"이라며 도구를 하나도 쓰지 않고 작업을 거부했다(그 턴의 `num_turns`가 1). 실제로는 실행 한도에 도달하지 않았다. 거부 직전까지 쓴 추정 비용은 r2 0.41달러, r3 0.23달러이고, 두 실행 모두 상태는 정상 완료다. 그래서 r2·r3은 뒤 단계가 구현되지 않았다. 계약 테스트 실패(r2 8개, r3 11개)는 모두 거부한 단계의 항목이다(r2는 D7, r3은 D6과 D7). 이 거부가 standing 주입 때문인지는 알 수 없다. 3회 중 2회에서 처음 본 현상이고, 원인을 따로 확인하지 않았다.

이 거부는 K8 수치에도 영향을 준다. 거부 턴의 응답은 짧은 한국어 문장이라, r2·r3의 첫 압축 뒤 한글 비율을 올리는 쪽으로 작용한다. r2·r3에서 에이전트가 실제로 작업한 마지막 턴(r2 S6, r3 S5)은 K8 위반이었다.

K7a 위반은 r1 S7, r2 S7, r3 S5·S6·S7에서 커밋이 없었던 것이다. r2 S7과 r3 S6·S7은 거부 턴이고, r1 S7과 r3 S5는 에이전트가 구현을 마치고 "커밋은 하지 않았습니다"라고 보고한 턴이다. 본 실행 9회에서는 K7a 위반이 없었다.

정리하면, 매 턴 재주입은 영어 전환을 줄였지만 없애지 못했다. r2·r3은 작업 거부가 섞여 구현 결과 비교에는 쓸 수 없다. 주 지표 위반율(실행별 3.1%, 3.6%, 4.1%)은 K8과 K7a 두 항목에서 나왔고, r2·r3은 거부로 비교 항목 수가 56개, 49개로 줄었다.

## 해석

지켜진 것과 깨진 것의 차이는 작업 폴더에 흔적이 남는지로 설명할 수 있다.

| | 예 | 흔적 | 압축 뒤 |
|---|---|---|---|
| 코드로 옮겨진 결정 | 잠금 방식, 패키지 구조, 테스트 이름 규칙, 커밋 메시지 접두어 | 코드, 설정, 커밋 이력 | 유지 |
| 대화에만 있는 지시 | 한국어로 답하기 | 없음 | 소실 |

이 과제에서 결정은 전달받은 턴에 바로 구현됐다. 그 뒤로는 요약이 그 결정을 빠뜨려도 코드를 보면 알 수 있다. 이름 규칙과 커밋 메시지 접두어도 기존 파일과 이력을 보면 따라 할 수 있다. 응답 언어만 저장소 어디에도 흔적이 없었다.

이 설명은 결과와 맞지만, 실험이 이 차이를 따로 분리해 검증한 것은 아니다.

## 한계

- 모델 하나(Haiku), 과제 하나, 조건당 3회다. Sonnet은 조건당 1회다.
- 과제의 결정은 대부분 전달받은 단계에서 바로 구현된다. "앞 단계에서 정하고 한참 뒤에 적용하는 결정"이나 "하지 않기로 한 결정"은 거의 없다. 실제 작업에서 압축으로 놓치기 쉬운 것은 이런 결정인데, 이 실험은 그것을 측정하지 못했다.
- 계약 테스트가 모든 조건에서 전부 통과했다. 압축이 구현 품질을 해치지 않았다고 볼 수도 있고, 과제가 그 차이를 드러낼 만큼 어렵지 않았다고 볼 수도 있다.
- 압축 한도를 10만 토큰으로 낮춰 압축을 일부러 자주 일으켰다. 한도 100만에서는 같은 과제가 맥락 40만 토큰까지 압축 없이 끝났다. Claude Code 기본 설정에서 압축이 얼마나 자주 일어나는지는 재지 않았다.
- 자동 메모리를 끈 조건이다. 켜면 결과가 달라진다.
- compact 조건에서 에이전트가 세션 기록 파일을 다시 읽으려는 것을 막지 않았다. Haiku 3회 중 2회, Sonnet 1회에서 그런 시도가 있었다.
- 실행 일부가 다른 실험과 같은 머신에서 동시에 돌았다. 실행 시간 비교는 참고만 한다.
- standing은 Haiku 3회뿐이고, 그중 r2·r3은 작업 거부로 뒤 단계가 비어 있다. 거부 턴의 한국어 응답이 standing의 압축 뒤 한글 비율을 올려 놓았으므로, compact·outbox와의 비율 차이를 그대로 효과 크기로 읽지 않는다. 거부의 원인은 확인하지 않았다.
- standing에서만 K7a 위반(커밋 누락)이 3회 모두 나왔다. 주입한 줄이 커밋 습관에 영향을 줬는지는 이 실험으로 알 수 없다.
- 토큰의 대부분은 캐시 읽기다(control 약 98%, 압축 조건 약 75%). Claude Code가 추정한 실행당 평균 비용은 control 2.29달러, compact 0.47달러, outbox 0.45달러다. 구독 토큰으로 실행해서 실제로 청구된 금액은 아니다.

## 이 결과를 어디에 썼나

[agent-discipline/harness](https://github.com/agent-discipline/harness)의 압축 대응 설계를 바꾸는 근거로 썼다. 원래 계획은 압축 직후 사용자 메시지 원문을 다시 넣는 것이었다. 이 실험에서 깨진 제약은 하나뿐이었는데, 그 방식으로는 그 제약을 지키지 못했다. 바뀐 방향은 세 가지다. 선택 질문과 답을 작업 폴더의 파일로 남긴다. 압축 뒤에는 작업 기록을 다시 읽기 전까지 구현을 막는다. 응답 언어처럼 계속 지켜야 하는 지시는 매 턴 다시 넣는다.

세 번째 방향(매 턴 재주입)의 확인 실행이 위 "후속 조건: standing"이다. 하네스 훅과 같은 문구를 넣었고, 영어 전환은 줄었지만 K8 기준으로는 3회 모두 위반이었다.

## 실행 환경

- Claude Code 2.1.326, 턴마다 새 컨테이너에서 `claude -p`로 실행하고 `--resume`으로 세션을 이었다.
- 모델: Claude Haiku 5.5, Claude Sonnet 5.5.
- 압축 한도는 환경 변수 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`로 정했다. compact, outbox, standing은 100000, control은 1000000이다.
- 실행 한도: 턴당 60분, 실행당 4시간, 6천만 토큰, 호출당 15달러(추정 비용 기준).
